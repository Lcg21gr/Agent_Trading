# Despliegue en Hostinger Business

La aplicación está preparada para el hosting Node.js de Business: un proceso HTTP, conexiones WebSocket salientes hacia cTrader y MySQL. Las lecturas pueden reutilizar la conexión con cierre tras 60 segundos sin uso; las escrituras usan una sesión nueva. No requiere Docker, Redis, un VPS ni un worker de estrategia. Hostinger publica un timeout por solicitud de 120 segundos; el transporte tiene un plazo total de 80 segundos, más las escrituras acotadas a MySQL.

`src/server.js` es el punto de entrada de producción: inicia el servidor al ejecutarse directamente o al cargarse mediante `import`/`require` por un proceso del alojamiento. Lee el `.env` situado en la raíz del proyecto y conserva los valores que Hostinger haya suministrado al proceso. La implementación HTTP reutilizable está en `src/app.js`, que puede importarse sin abrir un puerto.

1. Crear una **base MySQL dedicada** y un usuario desde hPanel. Guardar host, nombre, usuario y contraseña en las variables privadas `MYSQL_*` de la aplicación Node.js. Usar el host de base indicado por hPanel. Para una base remota, usar TLS verificado mediante `MYSQL_SSL_CA` y la configuración autorizada por el proveedor.
2. Crear o conectar la aplicación Node.js al repositorio. Seleccionar Node.js 22.13 o posterior (22 o 24 actualizado), tipo de aplicación `Other`, entrada `src/server.js`, comando de build `npm run build`, directorio de salida vacío/`none` y comando de inicio `npm start`. Es JavaScript ejecutado directamente: no necesita generar un directorio `dist`. El build comprueba la sintaxis y no conecta con MySQL ni cTrader. Ejecutar `npm run db:migrate` por separado en el entorno desplegado para crear las tres tablas propias de forma idempotente. La base debe ser dedicada; la migración conserva datos y no cambia tablas ajenas.
3. Añadir las variables de `.env.example` en hPanel y completar sus valores privados desde el `.env` local. No subir los TXT originales ni colocar `.env` dentro de `public_html`. Conservar el `PORT` que proporciona Hostinger; no fijar un puerto de escucha adicional. Iniciar con `TRADING_ENABLED=false`.
4. Asociar el dominio o subdominio y activar HTTPS. Usar un único hostname canónico para los clientes. Comprobar `GET /health` y luego `GET /ready` con Bearer: debe confirmar `brokerConnection: verified`, `persistence: verified` y `tokenTradingPermission: true`. Una respuesta de `/health` solo verifica HTTP.
5. Consultar cuenta, posiciones, historial y símbolo. Ejecutar `/v1/demo/orders/preview` con la instrucción prevista y verificar los límites. La salida hacia `demo.ctraderapi.com:5036` debe estar permitida por Hostinger; las pruebas desde el Mac no demuestran esa salida del alojamiento.
6. Configurar los límites de operación de esa cuenta y poner `TRADING_ENABLED=true`. Desde ese momento cada apertura/cierre requiere la clave de ejecución y su clave de idempotencia. Antes del uso operativo, validar una apertura y un cierre controlados en la demo y comprobar su historial. Esa prueba con el broker no está incluida en las verificaciones realizadas.
7. Respaldar MySQL y conservar `TOKEN_ENCRYPTION_KEY`. Al redesplegar, reutilizar base, Client ID, cuenta y etiqueta. No crear una base vacía para saltarse operaciones inciertas. Una restauración atrasada puede perder marcas de envío: conciliar con el broker antes de habilitar trading.

No se mantiene un bot entre peticiones. Las protecciones verificadas permanecen en cTrader y no dependen de que esta API siga abierta. Una operación incierta se conserva para conciliar tras un reinicio; una petición interrumpida no se interpreta como una orden fallida. La aplicación no garantiza disponibilidad continua de Hostinger ni monitoreo en segundo plano.

La optimización de lectura se activa por defecto al desplegar el código nuevo; no requiere nuevas claves ni migraciones. `CTRADER_REUSE_READ_SESSION=false` permite desactivar la reutilización y reconstruir/reiniciar conservando el resto del entorno. El alojamiento puede reiniciar procesos o cerrar conexiones inactivas: la consulta siguiente volverá a conectar y tardará más. Para comparar, medir varias consultas espaciadas y separar la primera de las siguientes; los tiempos locales de [performance.md](performance.md) no garantizan los de Hostinger.

Desde un servidor de confianza se pueden guardar las claves de API en el gestor de secretos del cliente. Para n8n, usar credenciales privadas de su nodo HTTP y reutilizar la clave de idempotencia de la misma instrucción en los reintentos. Para una web pública, pasar por un backend que autentique al usuario; no exponer la clave de trading en el navegador.

Referencia oficial consultada: https://www.hostinger.com/support/hostinger-node-js-limits-for-web-and-cloud-plans/ . Protocolo del broker: https://help.ctrader.com/open-api/proxies-endpoints/ y https://help.ctrader.com/open-api/messages/ .

## Diagnóstico del inicio

Para admitir todos los mercados del bróker, publicar la versión con soporte de comodín y configurar `ALLOWED_SYMBOLS=*` en hPanel. Conservar el resto de variables operativas. Tras reiniciar, `/v1/demo/capabilities` debe devolver `allBrokerSymbols: true`; `/ready` sigue verificando conexión y persistencia. La guía [markets.md](markets.md) explica los filtros por instrumento. Cambiar únicamente el entorno sin publicar el código con soporte de `*` causará un error de configuración en versiones anteriores.

El build correcto comprueba sintaxis; no demuestra disponibilidad del proceso de producción ni conectividad con cTrader. La suite incluye pruebas reales de proceso que ejecutan el punto de entrada directamente y mediante cargadores ESM/CommonJS, con un `.env` ficticio y sin credenciales de producción.

Al iniciar correctamente, los registros muestran `{"event":"api_listening",...}`. Si falla, muestran `{"event":"api_start_failed","code":"..."}`. Los códigos `CONFIG_*` identifican la validación de configuración que falló; `EADDRINUSE`, `EACCES` y `EADDRNOTAVAIL` distinguen fallos al abrir el puerto. No se registran valores de las variables ni errores remotos completos.

Si `/health` responde 200 pero `/ready` falla por persistencia, la respuesta identifica una causa conocida sin exponer datos del driver: `DB_ACCESS_DENIED` (credenciales o permisos), `DB_DATABASE_NOT_FOUND` (nombre de base), `DB_SCHEMA_NOT_INITIALIZED` (tablas pendientes), `DB_CONNECTION_REFUSED` (host/servicio), `DB_HOST_NOT_FOUND`, `DB_CONNECTION_TIMEOUT` o `DB_TLS_VERIFICATION_FAILED`. Los casos no reconocidos conservan `PERSISTENCE_UNAVAILABLE`.

Para la primera inicialización sin ejecutar npm por SSH, abrir phpMyAdmin desde hPanel, seleccionar la base dedicada configurada e importar [mysql-init.sql](mysql-init.sql). El archivo se generó de las mismas sentencias que utiliza `npm run db:migrate`; crea `trading_api_operations`, `trading_api_tokens` y `trading_api_agent_states`, sin borrar ni reemplazar tablas existentes. Si la API ya tenía historial y sus tablas se perdieron, recuperar y conciliar ese historial antes de inicializar otra vez.

Si el despliegue termina pero `/health` devuelve 503, revisar los registros de ejecución o `domains/talentouniversal.online/hbuilds/current/nodejs/stderr.log`. `/health` funciona sin consultar MySQL ni cTrader; un 503 HTML en esa ruta no confirma un fallo de esas integraciones. Verificar primero que Hostinger esté usando el commit corregido y la entrada `src/server.js`.

Para ampliar una instalación existente con históricos y estado por agente, ejecutar primero [mysql-agent-states.sql](mysql-agent-states.sql) en la base de la API y después publicar el código. `/ready` comprueba también esa tabla. No se requieren nuevas variables ni cambiar claves. Ver [agents-and-history.md](agents-and-history.md).
